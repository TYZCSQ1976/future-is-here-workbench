# 可靠多智能体工作流决策记录

## 背景

旧流程依赖 Codex 在自由文本中输出 `[PLAN_APPROVED]`。这个标记只能证明模型写出了一句话，不能证明事实有来源、风险已处理、验收标准可执行，也不能证明执行结果真的满足方案。

## 决策

采用一个模块化单体中的结构化五阶段工作流。以下名称指动态实例，不再固定绑定 Claude 或 Codex：

```text
用户目标
→ 用户指定的主笔实例生成结构化提案
→ 其余实例分别独立结构化审查
→ 服务端确定性共识判定
→ 用户人工批准
→ 用户指定的主笔实例生成结构化执行产物
→ 其余实例分别独立结构化验证
→ 服务端确定性验证判定
→ 用户审阅文件清单与补丁指纹并第二次批准交付
```

所有 AI 产物使用 `schemaVersion: 1`，并记录：

- 原始 Provider 输出；
- 运行时校验后的结构化对象；
- 面向用户渲染的 Markdown；
- Provider、模型标识、耗时、提示词版本和格式修复次数；
- 每个阶段的持久化检查点与可靠性判定。

## 确定性规则

模型不能自行决定“任务完成”。服务端只有在以下条件同时成立时才接受审查：

- 审查 verdict 为 `approve`；
- `issues` 为空；
- `unsupportedClaims` 为空；
- 所有 `checks` 都是 `pass`。

执行阶段只有在以下条件同时成立时才进入“待交付”，而不是直接标记成功：

- 验证 verdict 为 `pass`；
- 没有高危或严重残余风险；
- `requiredFixes` 为空；
- 所有验收检查都是 `pass`。

任何 `unknown` 都不会被当成成功。它表示缺少真实证据，需要用户补充或实际运行测试。验证通过后仍需用户第二次批准补丁交付，只有补丁安全套用到正式工作区后任务才成功。

## 失败与恢复

- 格式错误只允许一次有界自动修复，连续失败后安全停止；
- Provider 超时、空结果、异常退出或输出过大时记录失败，不绕过审查；
- 每次提案、审查、修订、执行和验证都写入检查点；
- 普通对话通过持久投递自动恢复；长程讨论或文件执行在重启时安全停止，已完成检查点仍可追溯并由用户重新发起；
- 独立验证失败进入 `needs_revision`，不会显示为完成。

## 被否决的替代方案

- 增加更多没有明确职责的 AI 角色：成本更高，但不自动提高可靠性。
- 用“多数投票”决定真伪：多个模型可能共享同一错误前提，票数不是证据。
- 继续依赖自由文本关键词：容易被提示注入、格式漂移和误判影响。
- 让 AI 直接修改正式工作区：候选修改必须先进入独立 Git worktree，经过结构化验证和第二次人工批准后才以补丁交付。

## 代价与复查条件

结构化协议会增加提示词长度和格式修复调用，也会让严格审查更容易停在“待修订”。当积累足够真实任务样本后，应建立版本化评测集，统计结构有效率、修复率、审查通过率、用户纠正率、延迟和成本，再决定是否调整字段与阈值。
