# Context Tree 团队记忆决策记录

## 要解决的问题

聊天历史很长，也混有猜测、过期方案和 AI 错误。如果把全部历史永久塞给每个成员，成本会不断增加，错误也会像谣言一样反复传播。

Context Tree 的作用类似“团队手册”：不是所有聊天都能进手册，只有有来源、适用范围并经用户批准的条目，才会成为后续任务上下文。

## 节点模型

每个节点至少包含：

- `scope`：适用的工作区，或 `global`；
- `type`：目标、约束、决定、架构或经验；
- `title/content`：人类可读内容；
- `source`：用户输入或产生建议的运行；
- `status`：`proposed`、`approved`、`rejected` 或 `superseded`；
- 决策人、决策时间和附加元数据。

## 使用规则

```text
用户手工添加 → 用户批准 → 可进入任务上下文
AI 形成方案/经验 → 只能 proposed → 用户批准后才可使用
任务开始 → 按工作区范围与关键词确定性筛选
→ 记录节点 ID + 内容摘要哈希
→ 作为不可信资料分隔后交给成员
```

摘要哈希用来回答“这次运行究竟参考了哪一版记忆”，不能证明内容本身为真。即使节点已批准，提示词仍把它当作资料而不是系统指令，防止节点内容越权改变权限或闸门。

## 当前边界

- 当前是轻量的有范围节点列表和确定性相关度排序，不是 First Tree 的完整图数据库；
- 尚未提供节点依赖边、冲突检测、自动过期和历史版本对比；
- 系统不会自动批准 AI 建议，也不会把“模型说已确认”当成用户决定；
- 用户仍需负责撤销过期条目，后续可以增加 `superseded` 的可视化替换流程。
