# 可靠控制面决策记录

## 要解决的问题

HTTP 请求和浏览器 SSE 连接都很短暂，但 AI 工作可能持续数分钟。若把任务状态只放在网页、进程内变量或一个 JSON 文件里，刷新、断网、重复点击和服务重启都会产生“到底做没做”的歧义。

大白话说：网页只是直播画面，不能兼任银行账本。账本必须记清谁领了任务、做了几次、结果是否先保存、用户看到哪一条事件。

## 当前设计

`src/state-center.js` 使用 Node 内置 SQLite 维护本机可靠控制面：

```text
用户提交 + requestId
→ runs 唯一键防止重复创建
→ deliveries 记录待领取/租约/重试/确认/死信
→ messages 先保存成员结果
→ ACK 确认投递完成
→ run_events 以递增序号供页面重放
→ sessions/*.json 保存易读的兼容任务投影
```

主要契约：

- 相同任务和防重复编号只对应一个运行；
- worker 通过有期限租约领取投递，不能永久占住工作；
- Provider 结果必须先写入消息账本和 JSON 投影，再确认投递；
- 页面按事件序号续接，旧事件不会重复展示；
- 普通对话在进程重启后恢复未确认投递；
- 多轮讨论和文件执行在重启时安全停止，保留检查点但不猜测外部模型半次调用是否完成；
- 健康接口只公开状态计数和聚合延迟，不公开数据库路径、提示词、令牌或完整对话。

## 为什么保留 JSON

SQLite 像“总账”，适合事务、唯一约束和并发；JSON 像“可读档案”，方便旧版本兼容、人工查看和导出。两者职责不同，JSON 不再承担可靠队列语义。

## 当前边界

- 这是本机单服务进程架构，不支持多台机器同时写同一数据库；
- Provider CLI 调用不能从中间 token 精确续跑，只能按已确认投递边界恢复；
- 尚未提供数据库自动备份、保留期和可视化审计后台；
- 协作事件与消息持久化，但长程协作尚未实现从任意轮次自动续跑，避免重复调用带来不确定副作用。
