# ADR 0003：用持久事件构建可核验的智能体轨迹

- 状态：已采纳
- 日期：2026-08-15

## 背景

旧版“轨迹”只显示少量起止或动作摘要。它像一张写着“厨师正在做菜”的便签：用户看不到用了什么工具、结果是什么、哪里失败，也无法在刷新或断线后完整复盘。DeepSeek Harness 已经把运行过程建模为仅追加的 `SessionEvent` 日志，这证明轨迹应当来自执行事实，而不是从最终回答反推。

## 决定

建立版本化的统一轨迹契约，并把它作为现有运行事件流的一部分持久化：

1. 每次 Provider 调用都有稳定的 `invocationId`；每个工具动作尽量有稳定的 `actionId`。
2. 事件统一包含类型、状态、标题、摘要、时间、来源和可见性；可选包含结构化输入、结果、耗时、Token 与错误。
3. Claude Code 与 Codex 从各自 CLI 的结构化事件流采集；DeepSeek Harness 从每次调用的隔离 SessionEvent JSONL 实时采集。
4. DeepSeek 原始日志仅用于当次采集，处理完成立即删除；进入工作台数据库前统一脱敏、限长和限制嵌套深度。
5. 页面按“运行 → 调用 → 动作”投影持久事件，支持搜索、筛选和按运行加载更早历史。
6. 不展示或猜测 Provider 没有明确给出的隐藏思维链；缺失细节使用 `provider_limited` 明示。

## 为什么不选择其他方案

- 只美化最终回答：无法证明动作真实发生，也不能解释失败。
- 抓取终端纯文本：不同 CLI 格式不稳定，难以可靠配对“开始/结果”。
- 永久保存 Provider 全量原始日志：可能包含大量对话或文件内容，隐私与存储风险过高。
- 把隐藏思维链当轨迹：既不可核验，也可能违反 Provider 边界；轨迹应展示动作与证据，不是假装知道模型脑内过程。

## 影响

- 好处：刷新、断线和切换任务后仍可重放；失败与取消明确；三种 Provider 使用同一界面契约。
- 代价：不同 Provider 提供的事件粒度不同；摘要经过脱敏与限长，不等于保存全部输出。
- 运维：轨迹仍受单次运行事件保留上限约束；达到上限时最旧事件会按现有运行事件策略淘汰。

## 重新评估条件

当 Provider 提供稳定的官方远程追踪 API、需要跨设备同步全量审计，或现有事件保留上限无法覆盖典型长任务时，重新评估专用轨迹存储与事件级分页。
