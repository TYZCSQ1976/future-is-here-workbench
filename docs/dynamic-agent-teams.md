# 动态多智能体团队决策记录

## 用户要解决的问题

固定的“Claude 提案、Codex 审查”只是一个流水线，不是一个可以临时组队的 AI 团队。用户需要在每个项目或任务中决定：谁参加、开几个同类分身、各自承担什么角色、谁负责汇总、讨论几轮，以及分歧最终如何处理。

## 核心模型

Provider 与智能体实例分离：

```text
Provider：Claude / Codex / DeepSeek（dsh，通过 headless 通道调用）/ 未来接入的模型
Agent Instance：本次任务中的一个独立分身
Team Role：用户为该分身临时指定的角色
```

同一个 Provider 可以同时创建多个实例，例如：

```text
Claude A：产品视角
Claude B：工程与架构视角
Codex A：安全审查
Codex B：测试与证据验证
```

每个实例拥有独立 ID、名称、角色、关注点、上下文和持久定向收件箱。讨论阶段采用上下文隔离；进入真实实施后，系统只给用户指定的主笔创建一个独立 Git worktree，其他成员在同一候选产物上只读验证。worktree 防止候选修改提前污染正式目录，但不等于操作系统容器。

## 双层身份视图

系统把“用户控制面”和“成员会议面”严格分开：

```text
用户控制面：知道底层是 Claude / Codex / DeepSeek，可以选择 Provider、数量和成本
成员会议面：只看到 member-1 / member-2、会议姓名、角色、关注点和主笔状态
```

服务端保存 `internal instance id → neutral member id` 映射，但不会把这张对照表加入任何参会提示词。成员需要明确知道自己正在参与一项由用户发起的正式团队协作，也知道所有成员（包括自己）都有本次专属分工；但不得推测、询问或讨论其他成员的底层实现和技术来源。旧任务中的 `Claude 1`、`Codex 1` 等技术名称在会议上下文里会自动转换为中性姓名。

消息路由使用 `toMemberId`，方案负责人使用 `member-N`；内部 Provider ID 只用于服务端调用、用户界面和诊断记录。

## 会议流程

```text
用户配置团队
→ 第 1 轮：所有实例互相不可见，独立思考
→ 后续轮：读取上一轮公开内容和发给自己的定向消息
→ 可以点名 question / answer / challenge / agreement
→ 用户指定的主笔实例汇总候选方案
→ 其他实例分别独立确认
→ 服务端计算共识状态并保留所有分歧
→ 用户最终批准或明确覆盖分歧
→ 主笔生成执行产物
→ 其他实例分别独立验证
```

## 共识规则

- `unanimous`：所有非主笔实例都确认；
- `majority`：超过半数确认，并且没有实例给出阻断结论；
- `user_decides`：不把分歧伪装成共识，完整展示后由用户决定。

人工闸门始终强制。机器共识只决定“方案是否具备提交给用户裁决的条件”，不能代替用户批准。用户覆盖分歧时，执行 API 必须收到显式 `acknowledgeDisagreement: true`；隔离实施完成后还必须经过第二次人工交付批准。

## 资源边界

团队最多 6 个实例、最多 5 轮交叉对话。Provider 子进程由全局队列限制，默认最多同时运行 4 个；其余实例等待，不会因为多个任务叠加而无限拉起本机进程。

## 当前限制与复查条件

- 用户可以直接配置角色，也可以选择 Claude 或 Codex 根据当前目标生成一份可编辑的组队建议；建议不会自动开始任务，也不会覆盖用户最终决定权；
- 每轮并行实例只能看到前一轮公开记录和已经投递给自己的消息，不能在同一轮实时插话；投递由 SQLite 收件箱记录领取、确认、重试和失败状态；
- 主笔只有一位，尚未实现多份候选方案并行竞争；
- 实例没有独立 CLI 长连接，记忆由服务端结构化上下文维护；
- 当前只有主笔拥有一个可写 worktree，尚未实现多个可写分身分别产出候选补丁、自动分析冲突并由用户择优；
- Git worktree 只是代码变更隔离，不限制进程能访问的整个操作系统；更强的容器沙箱、网络策略和按任务费用预算仍需后续实现；
- 系统能保证不主动提供 Provider—成员映射，但无法从技术上阻止模型根据表达风格自行猜测，也不能删除用户目标中原本就需要讨论的 Claude/Codex 等产品名称；这些内容不构成身份映射证据。

当积累真实使用数据后，应评估不同团队规模、轮数、共识规则对延迟、费用、格式失败率、用户纠正率和任务成功率的影响。
