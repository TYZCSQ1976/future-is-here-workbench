# 对话模式多智能体调度决策

## 背景

旧版“双 AI”会同时启动 Claude 与 Codex，但使用 `Promise.allSettled` 等两者全部结束后才一次返回。页面只显示一个思考动画，因此较慢成员会遮住较快成员已经完成的结果，用户也无法分辨谁在运行、谁已失败。两个回答彼此不可见，不构成真实协作。

First Tree 的公开实现强调显式参与者、消息唤醒、共享持久聊天、实时活动/失败状态和同一聊天内的交接。本项目保持本地单机范围，借鉴这些协作原语，但采用 Node 内置 SQLite 作为可靠控制面，不引入云端 Hub、WebSocket 消息代理或常驻 Provider 守护进程；项目记忆以经过用户批准的轻量 Context Tree 实现。

## 决策

对话模式由 `src/chat-runtime.js` 负责可靠运行，`src/chat-coordinator.js` 保留纯协作编排规则。路由只创建运行并建立 SSE 事件流；后台运行器负责投递领取、Provider 调用、结果落盘、确认、重试和恢复。

双 AI 支持两种由用户明确选择的方式：

1. `independent`：两位成员并行独立回答，完成一个就持久化并通过 SSE 推送一个；
2. `cross_check`：先执行相同的独立轮，两位都成功后再并行执行一次互相确认轮，然后确定性停止。

发言顺序不与 Provider 绑定。独立轮中谁先完成谁先展示；互证轮双方读取彼此初步观点，但提示词只暴露中性会议身份，不暴露底层 Provider。任一成员失败时保留其他成员结果；不足两份初步意见时跳过互证并记录部分成功。

Codex JSONL 解析取最后一个完成的 `agent_message`，避免把过程中的“我先检查”误当最终回答。

## 放弃的方案

- 固定 Claude 先提案、Codex 后审查：角色与任务无关，也会让前者延迟完全阻塞后者。
- 永久轮流发言：成本和时长不可控，容易形成循环和伪共识。
- 两个独立回答捆绑返回：实现简单，但无法实时显示、部分成功或恢复失败。
- 直接移植 First Tree：其多租户数据库、云端控制面和守护进程超出本地个人工作台当前需要。

## 影响

- 双 AI 默认会进行四次 Provider 调用（两次独立回答、两次互证），可靠性更高但总成本更大；用户可选“独立并行”降为两次。
- SSE 连接只是“直播窗口”：断开或刷新不会中止 Provider；页面按事件序号重放，不重复展示。
- 每次发送都带防重复编号；相同编号重复提交只会复用并重放同一运行，不会再次调用 Provider。
- 结果先写入消息账本和 JSON 任务投影，再确认投递；进程重启后，普通对话会恢复尚未确认的投递。
- 双 AI 互证仍是有界两阶段流程，不允许智能体自行无限续聊；多轮协作则使用持久定向收件箱和确定性停止规则。

## 重新评估条件

当需要跨设备或多机部署、常驻 Provider 会话、流式 token 级恢复，或让智能体在无人监督时主动唤醒其他成员，应把当前单进程 worker 升级为独立 worker 服务，并保持现有运行、投递、事件和确认协议不变。
