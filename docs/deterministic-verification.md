# 确定性验证决策记录

## 背景

过去的“验证通过”主要来自复核成员输出的结构化 JSON。服务端可以拒绝 `fail`、`unknown` 和高危风险，但不能证明成员所写的测试证据真实发生过。

大白话说：检查报告格式正确，不等于考试真的考过。

## 决策

第一阶段只支持 Node 项目中两个标准脚本：

- `npm run check`
- `npm test`

方案进入人工闸门时，页面展示命令及 `package.json` 脚本原文，并保存检查计划指纹。用户批准后，执行者先在独立 Git worktree 修改文件；随后确定性验证模块实际运行已批准脚本，保存退出码、耗时、状态和脱敏后的输出摘要。

执行前会重新读取 `package.json`。如果脚本内容与批准时不同，系统拒绝执行新脚本，防止 AI 在获得批准后替换命令。

确定性结果与 AI 复核是两个独立证据来源：

```text
系统命令全部退出 0
+ 所有 AI 复核者通过
→ 可以进入最终补丁交付闸门
```

任何系统命令非零退出、超时、启动失败或计划变化，都会进入待修订；AI 输出 `pass` 不能覆盖。

## 被否决的方案

- 让 AI 自由生成验证命令：模型输出是不可信数据，不能直接授权本机命令执行。
- 自动执行仓库内所有可能的检查：命令范围和成本不可预测，也无法让用户在批准前理解影响。
- 只保存 AI 的测试描述：不能形成可复核的退出码证据。

## 安全与恢复

- 使用固定可执行程序和参数数组启动 `npm`，不把用户文本拼进命令；
- 禁用隐式 pre/post 生命周期脚本，只运行用户看到的主脚本；
- 子进程继承精简环境，不继承 Provider 令牌；
- 每条命令有超时和输出上限；
- 常见令牌、密钥和 Bearer 值在保存前脱敏；
- 结果随实施运行持久化，刷新后可在交付闸门重新查看；
- 重复的实施提交仍受现有任务状态和运行防重复机制限制。

## 当前限制与复查条件

- 当前只识别根目录 `package.json` 的 `check` 和 `test`，尚不支持 Python、Rust、Go、子包或用户自定义检查；
- `npm` 项目脚本本质上仍是可执行代码，worktree 不能提供容器级文件系统或网络隔离；
- 输出脱敏只覆盖常见凭据形式，不能保证识别所有私密数据；
- 没有受支持脚本时允许继续 AI 复核，但界面必须明确标记“仅 AI 复核”。

当真实任务证明需要更多生态时，应逐个增加可审阅的验证适配器，而不是开放任意 shell 文本。
